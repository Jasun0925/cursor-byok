# PR424 完善方案：保留 Task 执行与结果交付

状态：本文件记录实施前设计。候选修复现已在隔离分支实现，自动测试通过，实机验收仍待完成；参见 [修复结果](2026-09-29-pr424-fix-result.md)。依据当前 fork `973fca3efe3c0aae11b84faf57b01405138a430b`、#424 `9def2906ee87baa3c127662c560044bb40e480d7`，以及同日 Cursor 实机证据。

## 结论

#424 应保留，但只解决 exec ID 被误标记的问题。完整修复应将“结束当前模型等待”与“取消子代理执行”分开，并让保留的 Task 通过会话级完成事件交付结果。不能只取消三个位置的过滤，也不能覆盖已经发送给模型的历史工具结果。

当前完整路径：

```text

  → output.queue_injection

  ├─ output 另将所有未完成 call ID 放入 interrupted_tool_calls
  └─ registry → BreakMessages
       → tool_round 为所有未完成工具提交中断错误，结束本轮等待
```

## 必须一起处理的四个问题

1. **执行层误过滤**：应用 #424，让保留的 Task exec 不进入 interrupted 集合；普通工具继续按原规则取消。
2. **结果层误过滤**：`output.rs:938` 将 Task 与普通工具一起标记，`output.rs:798` 因此直接丢弃晚到结果。必须区分“已取消”与“已解除前台等待但仍运行”。
3. **工具轮已结算**：`tool_round.rs:131` 统一提交中断错误。即使跳过 output 过滤，晚到结果也不能再按普通 ToolResult 提交给已结束的工具轮；否则可能串入新轮或触发协议错误。
4. **接收者提前结束**：output 在 RunEvent::Ended 时退出，runtime 仍向 generation.results 投递；发送端忽略通道关闭错误。父轮结束后还有约 2 秒的 continuation idle 超时。仅修正过滤无法保证更晚的 Task 结果到达。

另外，call ID 只在 round 内唯一（数据库 UNIQUE(round_id, call_id)）。跨轮保存的状态和去重不能只用 call ID；必须保留原 round 身份，并区分原 generation 与替代运行。

## 建议结构及职责变化

```text
server/src/
├── cursor/tools/runtime.rs             # 应用 #424；只管理 exec 的执行/取消
├── cursor/conversation/
│   ├── task.rs                         # 新增：保留 Task 的原始归属、状态和完成事件身份
│   ├── runtime.rs                      # 持有该状态；在父输出循环结束后仍接收结果
│   └── output.rs                       # 只协调前台模型响应和 checkpoint，不持有晚到 Task 的唯一接收权
├── cursor/compile/insert_messages.rs    # 提取/复用现有完成消息投影，避免另造一套提示词
├── run/
│   ├── command.rs                      # 显式传递本次中断中“转为异步等待”的调用身份
│   └── tool_round.rs                   # 普通工具写中断；保留 Task 写真实的继续运行状态
└── store/messages.rs                   # 复用稳定事件 ID 和现有事务去重，不改写旧历史
```

这是拟议结构，不是当前已实现结构。职责移动：保留 Task 的识别与晚到结果交付，从 output 的局部集合/接收通道提升到 conversation runtime。新增一个小而专用的 task 模块，不引入通用任务调度框架。不搬迁 provider 适配器，不修改工具轮 SQLite 状态枚举来混淆“前台调用已返回”与“子代理已结束”。没有必要为此拆分其他无关模块。

具体 API 设计应让 Cursor 层决定哪些调用保留，run 层接收明确的调用身份及结算语义；不要让通用 run 层到处判断 Cursor 工具名字符串。call 身份建议包含原 run/round/call；exec ID 仅用于该协议生命周期的路由。

## 目标时序与历史

```text
原父 Run / 原 Task 正在执行
  → Steer 到达
  → 先登记 Task 转为异步交付，保持原 exec 和子代理 ID
  → 结算前台 Task 调用：成功返回“仍在运行，结果随后送达”
  → 追加用户补充消息
  → 父模型继续响应（例如“已收到补充”）
  → 原 Task 完成
  → 会话 runtime 接受并去重原 Task 结果
  → 追加新的 task-completion 运行时消息
  → 当前父 Run 在安全边界消费，或父 Run 已结束时启动完成消息后续轮
  → 模型报告随机标记；checkpoint/数据库保存同一结果
```

“转为异步交付”不意味着重启子代理，也不意味着再次调用 Task。原 Task 的执行生命周期不变；仅在父 Run 已结束时才创建父对话的后续运行。

模型历史保持追加：

```text
… → Task 工具调用 → Task 继续运行的返回值 → 用户补充
  → 父回复 → Task 完成通知（包含原调用身份、子代理 ID、成功/失败和输出）
  → 父最终回复
```

不得把已经发给模型的“继续运行”返回值回写成最终结果，也不得再给同一 tool_call_id 补第二条 tool result。最终结果作为新的运行时完成消息。

## 生命周期与竞态

| 条件 | 必须行为 |
| --- | --- |
| Task 结果已被前台提交，随后消息到达 | 保留原成功结果，不再次生成完成通知 |
| 消息先到，Task 结果在切换途中到达 | 以唯一状态转移决定正常完成或异步完成，只接受一次 |
| 父 Run 仍运行 | 使用已有 InsertMessages 的安全边界追加，不打断新的普通工具 |
| 父 Run 正在 Finalizing / 已结束 | 完成事件不能仅留在 registry.pending；复用后台完成的后续运行路径主动消费 |
| 父回复已结束，但 Task 未结束 | 在仍有效的原 transport 生命周期内保留接收权；不能被固定 2 秒超时清走 |
| 同一结果被重放或不同通知通道重复报告 | 稳定事件 ID + 原 round/call/子代理身份去重，历史仅追加一次 |
| 下一工具轮复用了相同 call ID | 必须按原 round 路由，不误匹配当前轮 |
| 用户显式停止、运行被替换或真实断连 | 遵守原有取消边界；不得在用户停止后自行唤醒旧任务 |
| 普通 Read/Shell 等被中断 | 保持取消并丢弃其晚到输出，不受 Task 保留逻辑影响 |

现有 BackgroundTaskCompletionAction 路径已经处理 active/finalizing/ended 三种情况，优先提取共享行为。不要只调用 registry.deliver 然后认为它会自动启动运行：无 active run 时它只入内存队列。也不要假设前台 Task 在被 Steer 后必然额外收到 Cursor 的后台完成通知，本次实机仅确认收到 ExecClientMessage.subagent_result.success。

跨服务重启恢复不由内存状态保证；如果要承诺此能力，必须另行设计持久化所有权和恢复协议。当前修复至少保证已收到完成事件的历史提交与重放幂等，不以无限延长所有 transport 超时作为解决办法。
