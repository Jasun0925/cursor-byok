# PR #513：SQLite 事务失败后的连接池恢复

基线：`1b0a851edeacba24d293ba30fb0d9c55b16f742d`。来源：[banchen21 的 PR #513](https://github.com/leookun/cursor-byok/pull/513)，head `87ee81dced16f0342b610e0a47d4f9b8e2515db8`。2026-10-27 查询仍为 OPEN，仓库已归档；reviews、讨论、行内评论与 check runs 均为空。

本轮独立修复其中可复现的连接池污染，不整体采用 PR，也不重新合入其子代理入口改动。子代理入口已有 #477 的独立修复和回归；本轮不以数据库测试证明其他部分通过。

## 故障与复现

一次 SQLite 自动回滚之后，SQLx 0.8.6 的事务深度仍可能为 1。随后 `Transaction::drop` 排队执行 ROLLBACK，但数据库中已没有活动事务，ROLLBACK 失败且深度不清零。连接池的普通 ping 只确认 worker 可以响应，不检查这个计数，因此连接再次被取出后，`BEGIN IMMEDIATE` 返回 `InvalidSavePointStatement`。

这会使同一 Store 中后续会话写入失败；恢复需要丢弃污染连接，不能只让当前请求重试同一个连接。

在临时、文件型数据库上保留连接池的其他连接，使一个槽位反复经历失败与归还，防止随机取到另一条健康连接掩盖问题：

- 通过真实 `Store::ensure_conversation` 写入检查点时，由测试触发器 `RAISE(ROLLBACK, ...)` 让 SQLite 自动撤销事务；下一次正常会话写入失败。
- 自动回滚后显式调用 `Transaction::rollback`，返回“没有活动事务”；下一次会话写入同样失败。
- 普通延迟外键约束导致 COMMIT 失败、取消未提交任务、正常提交这三项原本通过。

**修复前：2 失败、3 通过。** 失败位置均为后续真实 `Store::ensure_conversation`，错误为 `Database(InvalidSavePointStatement)`，没有通过 `mem::forget` 人为跳过事务析构来制造结论。

## 修复边界

已核对实际依赖 SQLx 0.8.6 的 `PoolOptions::after_release`、`Connection::is_in_transaction`、SQLite worker 的 `Ping/Commit/Rollback` 和事务析构实现。

使用现有 SQLx 连接池的 `after_release` 钩子：如果仍有事务深度，先 ping 等待已排队的回滚完成；仍非零则返回 false，由 SQLx 关闭连接并为后续获取创建新连接。正常回滚把深度清零后继续复用。

```text
当前生产目录（行数包含注释与空行，测试单列）
server/
├── src/store/sqlite.rs                 # 65 行；池初始化与归还检查
├── src/store/writer.rs                 # 既有写入互斥，不改职责
├── src/store/{checkpoints,runs,...}.rs  # 既有事务与业务查询，不改接口
├── migrations/                        # 不改结构、迁移或校验和
└── tests/store_transaction_recovery.rs # 253 行；真实 SQLite 故障及恢复回归
```

```text
Store 业务写入 → SQLx Transaction → COMMIT / 失败 / 取消
                                  ↓
                        连接归还前 after_release
                                  ↓
                 等 worker 执行已排队的 ROLLBACK
                   ├─ 深度归零：归还原健康连接
                   └─ 深度未归零：关闭连接，后续获取新连接
                                  ↓
                     同一 Store 创建后续会话成功
```

原 PR 的 WriteSession 为每个调用点增加未提交关闭策略，还会丢弃已经干净回滚的健康连接。本修复集中在池边界，覆盖池中所有读写事务；正常约束失败和任务取消通过临时表标记确认仍复用同一条连接。没有新增包装层、手写事务协议或迁移，也不替请求吞掉原始错误。

## 验证范围

扩展到 7 项定向测试：

1. 实际 Store 写入中的自动回滚后恢复。
2. 显式 ROLLBACK 失败后恢复。
3. 自动回滚后 COMMIT 失败后恢复。
4. 临时数据库通过 `PRAGMA max_page_count` 真正触发 `SQLITE_FULL`（错误码 13），撤销此前未提交的会话和 blob 写入，解除容量限制后继续创建会话。
5. 延迟外键约束 COMMIT 失败，不保留无效数据，复用原健康连接。
6. `tokio::task::abort` 取消未提交写入，数据回滚并复用原健康连接。
7. 正常提交后数据可读取、检查点完整、连接继续复用。

7 项均通过；`cargo test --locked --workspace` 共 **446 通过、0 失败、0 忽略**（35 个结果组，含桌面与文档目标），工作区全目标 Clippy、格式和差异检查通过。全量验证结果写入 [结构化证据](2026-10-27-pr513-evidence.json)。测试使用独立临时数据库，没有访问正式用户库，没有填满文件系统；SQLite 数据库容量限制只作用于测试连接。没有修改日志/历史保留策略，不能把这项修复当成 #511 数据库体积问题的解决。

原作者机器的磁盘、进程与 Cursor UI 未现场复测；结论限定为已实际复现的 SQLite/SQLx 状态错位和后续 Store 恢复。源码修复尚未发布安装包。
