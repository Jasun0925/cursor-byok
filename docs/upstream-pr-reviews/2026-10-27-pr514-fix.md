## 复现与结果

当前内置 OpenAI Chat/Responses 的公共函数把 GPT 模型的 `prompt_cache_key` 固定写成 `cursor-byok`，没有使用已有会话 ID。模型测试也会携带这个固定键；插件侧则直接使用会话 ID，两个入口规则不一致。

改动前先加入行为测试：

- 实际 HTTP 请求期望 `cursor:conversation-a`，收到 `cursor-byok`，失败。
- 通过 ControlService 执行 GPT 模型测试，期望请求没有缓存键，实际仍包含，失败。
- 既有两项 Responses 连通性测试通过，确认失败与新增断言有关。

修复后：

| 调用 | 缓存键 |
| --- | --- |
| 同一会话的新回合、工具轮次和重试 | `cursor:<conversation_id>`，不取决于 run/call ID |
| 不同会话 | 不同缓存键 |
| 模型连通性测试 | 原生请求省略 `prompt_cache_key`，插件 wire 为 `cacheKey: null` |
| 内置非 GPT 模型 | 保持不发送该字段 |

缓存键是请求级字段。没有改写已有消息、检查点、规则、工具定义、压缩内容或数据库 schema；部署后旧会话的请求键会切换一次，不能据此承诺缓存命中提升。

## 职责与数据流

```text
server/src/
├── run/engine.rs                       # 正常及压缩调用启用会话缓存
├── control/service.rs                  # 连通性测试显式禁用缓存键
├── model/inference.rs                  # ModelInvocation 统一派生可选缓存键
├── provider/{mod,openai_chat,openai_responses}.rs # 原生请求写入可选键
├── plugin/wire.rs                      # 插件使用相同键或 null
├── api/byok/mod.rs                     # 显式选择外部调用缓存策略
└── cursor/services/commit_message.rs   # 显式选择提交说明调用缓存策略
server/tests/
├── provider_cache_key.rs               # 抓取两种协议的真实 HTTP 请求体
└── model_connectivity.rs               # 通过真实控制服务入口验证两种协议
```

控制入口/运行循环 → ModelInvocation（会话 ID + 缓存策略）→ 原生或插件序列化 → HTTP 请求。已有调用记录身份和持久化路径保持原有职责。
