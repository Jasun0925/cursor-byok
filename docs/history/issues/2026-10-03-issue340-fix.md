## 客户端证据

只读检查本机 Cursor 3.23.12 的 `workbench.desktop.main.js`，没有修改应用：

- `rKf` 的 interactive-child 完成通知不设置 `toolCallId`；`taskId` 由父子关系和 `turnId`（缺省用 `runId`）组成。
- `Ncy` 将 `toolCallId: e.toolCallId` 直接映射到协议字段。
- 本仓库 `protocols/cursor/agent_v1.proto` 的 BackgroundTaskCompletion 第 10 字段明确为 `optional string tool_call_id`。
- 客户端代码支持该通知格式，不等同于本次已捕获真实 UI 发出的请求。

```text

└── tests/conversation_delivery.rs        验证已结束父轮次的恢复、历史前缀及通知重试
```

```text
Cursor AgentRunRequest / BackgroundTaskCompletionAction
  → 编译通知：校验必填字段、按事件身份排序
  → conversation registry 投递
      父 Run 活跃：插入既有 Run，继续当前生命周期
      父 Run 正在结束：排队，等待结束并读取最新检查点
      父 Run 已结束：排队，创建父会话的新 Run
  → RunEngine 追加供应商历史 → 模型响应
  → SQLite 持久化 → KV 确认、检查点及成功终止帧
```

本次只修改通知编译及测试；投递、模型循环和持久化沿用现有实现，没有移动或新增运行时模块。

完成事件身份使用 JSON 元组 `(kind, task_id, subagent_id, tool_call_id)`：

- 缺少工具 ID 可以正常处理；子代理 ID、任务 ID、标题及种类/状态校验保留。
- 同一子代理的不同任务轮次由 `task_id` 区分，即使共享工具 ID 也不会合并。
- 相同通知重试保持相同身份；结构化编码避免字段分隔符碰撞。
- 不改写早先历史、不增加旧身份兼容层；升级前已经持久化的旧格式事件若再次重放，不承诺跨版本去重。
