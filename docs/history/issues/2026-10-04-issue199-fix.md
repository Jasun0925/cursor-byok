# Issue #199：MCP 工具 required:null 导致参数 schema 校验失败

> 历史记录：状态、版本、路径及测试数仅对应记录日期；当前交付状态见 [工作状态](../../work-status.md)。复现脚本按文中基线使用，不作为当前生产操作步骤。

本地复现并修复了一个能产生同类错误的 MCP 输入路径；没有证明原作者公益站报错的唯一根因，也没有使用真实 Grok 服务复测。

原报告：[leookun/cursor-byok#199](https://github.com/leookun/cursor-byok/issues/199)。2026-10-04 查询状态为 OPEN。原错误核心是 `/required: null is not of type "array"`。原帖没有完整出站请求，因此不能由此推断 tools、tool_choice 或 stop 字段都应补成空数组。评论称切换 Responses 可用，这不是本次修复依赖的方案。

## 定位与修复范围

当前内置工具未发现 required:null。MCP schema 经 JSON 或 protobuf 输入时，现有 `normalize_mcp_parameters` 会检查根对象和 properties，但保留 required:null。Chat 与 Responses provider 都会照此发送。

```text
AgentRunRequest / RequestContext 的 MCP 定义
  → server/src/cursor/compile/context.rs       # 解析并规范化参数 schema
      required:null → required:[]
  → server/src/cursor/prompting/compiler.rs    # 编入稳定工具列表
  → server/src/provider/openai_chat.rs        # tools[].function.parameters
    或 provider/openai_responses.rs           # tools[].parameters
  → 供应商接口
```

只处理参数 schema 顶层显式的 required:null，按“无必填参数”转换为空数组。缺省 required 不新增字段；合法 required 列表、properties 内名为 required 的参数、default/examples 中的 null、联合分支与其他约束保持原样。原始 MCP wire 定义仍用于客户端工具调度，未改写；没有改会话或数据库。

此为 Cursor MCP 编译入口的修复，不是所有 JSON schema 的递归修复，也不改写外部 API 原生透传、插件自行定义的工具或额外参数覆盖。

## 验证

- 先新增 Chat/Responses 严格校验 HTTP 模拟端点用例：修复前 2 项均失败，实际收到 required:null 后返回同类 HTTP 400。
- 修复后相关 8 项全部通过，其中新增 4 项：Chat 请求、Responses 请求、仅规范化 schema 字段且幂等、protobuf schema 路径。
- HTTP 测试捕获实际请求体，确认 required:[]；重复调用请求完全相同，原始 MCP wire 保持不变。
- 服务端全量 324 项通过，Clippy（`-D warnings`）、格式及 diff 检查通过；详细结果见 [验证记录](2026-10-04-issue199-evidence.json)。

## 真实复测

使用原公益站的 Grok Chat Completions 模型，配合原 MCP 工具发起一次需要调用工具的对话。检查工具参数定义中的 required 是否为数组，并确认不再出现这条 400。若没有 MCP 工具，或 BYOK 出站已经是合法数组，继续检查原始请求和网关转换，不能套用本次根因。
