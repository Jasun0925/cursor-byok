# Issue #318：Responses 图片 `detail` 字段复核

> 历史记录：状态、版本、路径及测试数仅对应记录日期；当前交付状态见 [工作状态](../../work-status.md)。复现脚本按文中基线使用，不作为当前生产操作步骤。

## 结论

上游 [#318](https://github.com/leookun/cursor-byok/issues/318) 报告严格 vLLM 后端因 `input_image` 缺少必填 `detail` 返回 400；上游维护者随后评论“应该修复了”。当前 main 的 `server/src/provider/openai_responses.rs` 已生成 `detail: "auto"`，因此没有重复修改生产逻辑，本次补充回归测试并确认历史重放不会丢字段。

这证明个人 fork 当前代码覆盖了报告中的具体缺口；没有使用原作者的 vLLM、图片请求或生产 API，不能把自动化验证描述成原环境现场复测。

## 执行路径

```text
Canonical Message (ContentPart::Image)
  → model::project_messages
  → provider/openai_responses::responses_input
  → responses_content
  → {type: input_image, detail: auto, image_url: data URL}
  → OpenAI Responses / 严格兼容后端
```

历史消息使用相同的 `responses_content` 投影路径，所以第一轮图片输入和后续携带图片历史都会得到完整字段。`openai_chat` 使用独立的 Chat 图片结构，不受本字段影响。

## 新增验证

- `image_input_contains_required_detail_for_strict_responses_servers`：PNG 图片序列化包含 `type=input_image`、`detail=auto` 和正确 Base64 data URL。
- `image_detail_survives_history_projection`：JPEG 图片经历史投影再次序列化时仍保留 `detail=auto`。

验证结果：服务端全量 `cargo test -p cursor-server --all-targets` 共 20 个测试目标、309 项通过、0 失败、0 忽略；Clippy（所有目标、警告视为错误）、格式检查、差异空白检查通过。使用本机 macOS 26.5 SDK 和 Rust lld 链接器。
