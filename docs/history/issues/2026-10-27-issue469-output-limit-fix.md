## 证据

在[真实链路验收](2026-10-27-issue469-snapshot-live.md)中，18,144 个允许文件的元数据只收到 832,960 字节，随后进程退出 0，JSON 不完整。不能把退出成功当成传输完整。

本机及远端 Cursor 3.27.14 的 `cursor-agent-exec/dist/main.js` SHA-256 相同：`66c26ae001b20362c5f8b0169e2cf752e81e1fa98dac6056b1ba86f9c2292291`。复用先前 REA 对相同 artifact 的静态分析身份，再进行普通文本定位，发现 Shell 执行层有独立的 **1,048,576 字节内联 stdout 上限**。只有“已经发送的字节数 + 当前整块长度”不超过上限时才发送该块；跨过上限的整块被丢弃，因此返回内容可能少于 1 MiB。`fileOutputThresholdBytes` 只控制另一路文件输出，不提高内联上限。

[结构化静态证据](2026-10-27-issue469-output-limit-evidence.json)保留文件摘要、字符/字节偏移和具体匹配位置。没有执行或修改 Cursor bundle。静态分支与实际不完整输出相互印证；这不意味着所有大输出故障都只有同一原因。

新增实际主机回归先失败：950,000 字节源码生成的原始正文响应为 **1,266,801 字节**，超过客户端上限，证明原有 2 MiB 正文批次同样需要分页，不只是元数据。

## 现在的执行路径

```text
server/src/search/snapshot/
├── collect.py     # 主机重新生成完整响应，按摘要与偏移返回一页（262 行）
├── transfer.rs    # 请求内重组分页，校验长度、顺序和 SHA-256（156 行，含内嵌测试）
├── mod.rs         # 收齐响应后才推进元数据选择或正文批次（208 行）
└── command.rs     # 通过现有 POSIX / PowerShell 启动器携带分页参数

主机生成本阶段完整 JSON → SHA-256 + 总长度
  → 每页最多 256 KiB 原始 JSON 字节 → base64 页信封
  → 一次 Cursor Exec stdout（小于 512 KiB 接收预算）
  → BYOK 检查 offset / total / 摘要 / 页长度
  → 尚未完整：下一次 Exec 重新生成同阶段响应，摘要须一致
  → 已完整：校验完整 SHA-256 → 解析原结果 → 继续下一阶段
```

行数包含注释、空行；独立 `tests.rs` 未计入上表，`transfer.rs` 的内嵌测试已明确计入。元数据和正文共用同一分页层；取消仍归原 Semble 调用所有，内部页面不成为模型工具结果。

每阶段完整响应保留 5 MiB 上限，工作区仍为 20,000 枚举项、16 MiB 选中正文、1,000,000 字节单文件；没有通过降低工作区容量规避错误。每页请求都重新检查实际工作区，不落临时快照、不回读 BYOK 主机同名路径；中途变化、重复/跳过页、错误长度或摘要都整体失败。代价是大响应每页会重新生成本阶段内容，后续还需观察实际性能。
