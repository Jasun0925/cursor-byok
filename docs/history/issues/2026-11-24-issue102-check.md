# Issue #102：Responses 工具 ID 历史回放复测

**结论：当前版本自动化未复现，无生产代码改动。** 两项新回归覆盖 Chat → Responses 切换和 Responses 自身回放；工具调用经过 SQLite 保存、关闭连接后重新读取、Cursor 检查点编解码，最终 HTTP 请求仍使用原始 `call_id` 配对结果，不把它写入 `id`。原作者的旧数据库、真实 Cursor 操作和供应商校验未验收，不能标为原问题彻底解决。

## 原报告与基线

- [上游 Issue #102](https://github.com/leookun/cursor-byok/issues/102)，2026-11-24 查询仍为 OPEN；正文报告继续旧对话时出现 `Invalid input[3].id ... Expected an ID that begins with fc`。
- 作者提供的线索是旧工具历史同时保存了相同的 `provider_item_id` / `provider_call_id`；其中 `call_...` 被发送到 Responses `input[].id`。这属于报告方的诊断，本轮未取得其原始请求或旧 `context.json`。
- 可见评论只有维护者表示稍后修复；查询时间线未发现关联 PR。
- 本轮源码基线：`aae57073e0744a5ca7a8fb5a7c0357e21d91b3a0`，已发布版本 v1.2.1 的后续文档提交。
- [OpenAI Responses 请求文档](https://developers.openai.com/api/reference/resources/responses/methods/create) 将 function call 的 `id` 列为可选字段；无需为了回放 Chat 工具调用而生成一个假的 `fc_...`。

## 当前执行路径

```text
server/
├── src/provider/openai_chat.rs       # 从 Chat tool_calls[].id 提取调用 ID
├── src/provider/openai_responses.rs  # 从 Responses call_id 提取调用 ID；回放时不生成 item id
├── src/run/model_cycle.rs            # 汇集流式工具调用及完整参数
├── src/model/message.rs              # 规范消息保存 call_id，不保存旧 provider_item_id 字段
├── src/store/                        # 保存并重新加载不可变检查点和规范消息
├── src/cursor/checkpoint/messages/   # Cursor 检查点编解码，保留工具配对 ID
├── src/model/projection.rs           # 将规范历史投影为供应商请求消息
└── tests/responses_tool_history.rs   # HTTP/SSE、SQLite 重开与检查点回放回归
```

```text
受控 HTTP/SSE 工具响应
  → 生产 provider adapter → model cycle
  → 用 cycle 结果构造规范历史（工具结果为测试夹具）
  → SQLite import_checkpoint → 关闭连接 → 重新连接并加载
  → Cursor stable_messages → decode → project_messages
  → Responses HTTP 请求：function_call.call_id = function_call_output.call_id
  → 追加用户问题再发请求：此前 input 保持完整结构前缀
```

两条场景分别使用 Chat 的 `id=call_issue102_read`，以及 Responses 中彼此不同的 `id=fc_issue102_item` 和 `call_id=call_issue102_read`。断言实际出站请求中的工具名、参数、结果内容、配对 ID 和调用数量，确认 `function_call` 未输出 `id`。这证明当前投影链路的字段边界，未运行完整 Agent 生命周期，也不证明真实模型会按夹具选择工具。
