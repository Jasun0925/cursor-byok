# Issue #482：MCP 工具对象 schema 补全

> 历史记录：状态、版本、路径及测试数仅对应记录日期；当前交付状态见 [工作状态](../../work-status.md)。复现脚本按文中基线使用，不作为当前生产操作步骤。

## 结论与证据边界

上游 [#482](https://github.com/leookun/cursor-byok/issues/482) 报告 Cursor 3.22.7 的 Ask 模式调用 LM Studio 的 qwen3.8-27b 时，Responses 接口返回 `400 / Invalid input / tools.18 / custom`，而模型连通性测试成功。本次查询该 issue 为 OPEN、没有评论，正文没有 LM Studio 版本、完整工具列表或请求体。

当前 Ask 静态工具共 17 个，不能仅凭索引 18 推断原工具名称；额外工具来自客户端的 MCP 定义等上下文。本次没有原请求，不认定发现的缺口就是原报告的唯一根因。

已确定并修复的缺口：现有 MCP 编译器原样接受 `{"type":"object"}`，导致模型请求没有根级 `properties`；也会拒绝完全空的 `{}`。这与严格对象工具校验存在互操作问题。

参考证据：

- LM Studio 公开 SDK 的 [LLMToolUseSetting.ts](https://github.com/lmstudio-ai/lmstudio-js/blob/a883894645a2a1b70e48902eff87c3b3f141a215/packages/lms-shared-types/src/llm/LLMToolUseSetting.ts) 定义 `llmToolParametersSchema`，要求 `type: object` 和 `properties` 记录；`required` 是可选字段。此文件不是已安装 LM Studio Responses 服务的完整源码。
- LM Studio 自身 [#2254](https://github.com/lmstudio-ai/lmstudio-bug-tracker/issues/2254) 报告 0.4.20+1 对 `parameters: {}` 返回相同形式的 `tools.N / Invalid input / custom`；改为显式对象和空属性表后成功。该报告来自另一用户和另一模型，作为相关证据使用。
- BYOK 的 `ControlService::run_model_test` 使用空工具列表，解释了“模型测试通过”不能覆盖 Agent/Ask 的工具 schema 校验。

## 修改结构

```text
server/src/cursor/compile/
├── context.rs            将客户端 MCP schema 编译为供应商可用的对象定义
└── tool_schema_tests.rs  验证 MCP 编译、Ask 工具组装、Responses HTTP 序列化和重试稳定性
```

```text
客户端 AgentRunRequest / RequestContext.tools
  → dynamic_mcp 读取 schema，保留原始工具描述用于客户端派发
  → normalize_mcp_parameters 只补全模型侧对象定义
  → PromptCompiler 按稳定顺序组装 Ask 静态工具与动态工具
  → OpenAiResponsesProvider 序列化 tools
  → HTTP 校验 → SSE 完成事件
```

运行中的模型循环、消息持久化和检查点恢复保持原实现；本次不改写已有历史，也不新增供应商私有的降级分支。

规则：

- 空 `{}` 在工具参数必须为对象的上下文中，明确化为 `{"type":"object","properties":{}}`。
- 已声明对象但缺少根级 `properties` 时补 `{}`；已有属性原样保留。
- 现有仅含对象分支的 `anyOf` / `oneOf` 继续保留分支，补全根级声明与属性表。
- 不新增 `required` 或 `additionalProperties:false`，不强制开启 strict，不展开引用、不丢弃工具。
- 非对象 schema、混合类型联合仍拒绝；错误类型的 `properties` 在本地按工具名报错。
