## 行为与边界

手动停止或 provider 流失败时，将当前调用已经产生的文字追加到持久化历史，并发布恢复检查点。自动重试和随后新建的 Resume 请求均能看到这些文字。追加的继续提示明确说明文字可能不完整，要求接着完成任务，避免重复已完成操作。

等待工具时取消，会保留该轮文字与已完成工具结果，仅为尚未完成的调用记录取消结果，并终止工具执行。恢复时不会自动重放已取消的工具；模型仍可根据用户新指令决定重新调用。

每次尝试使用独立、幂等的消息标识，重试只追加历史；连续失败不会替换上一请求的继续提示。恢复到新 transport 后验证 provider 可见的角色、内容保持前缀一致；内部消息 ID 的既有重建行为不在此次改动范围。未完成的 thinking 不作为有合法 replay/signature 状态的推理记录保存，未完成的压缩摘要也不写入普通对话历史。

## 执行路径

```text
server/
├── src/run/
│   ├── engine.rs                 # 获取取消或失败调用的部分文字，重建重试请求
│   ├── interruption.rs           # 追加中断文字、结算取消工具、等待检查点发布
│   ├── tool_round.rs             # 接收工具结果与取消，保留已完成调用
│   └── event.rs                  # 声明中断文字提交与工具取消提交事件
├── src/cursor/conversation/
│   └── output.rs                 # 发出取消工具卡片，并提交恢复检查点
└── tests/
    ├── issue172_repro.rs          # 四种中断及恢复的协议集成回归
    ├── error_lifecycle.rs         # 部分输出重试、替换旧请求的生命周期回归
    ├── interrupt.rs               # 工具终止、取消检查点与流结束的顺序回归
    ├── tool_presentation.rs       # 工具卡片先结束，文字再显示，检查点重放同序
    └── support/fake_provider.rs   # 控制事件流挂起与断流时点
```

```text
当前 run：模型文字已发给 Cursor
    → Cancel / provider 流失败
    → run 追加文字或结算未完成工具 → SQLite checkpoint
    → Cursor output 完成展示记录 → checkpoint 发布并确认
    → 当前 run 取消/失败，或用追加后的历史自动重试
后续 Resume / 新用户消息：客户端 checkpoint
    → 恢复历史 → provider 收到旧文字、工具结果及新指令
```

没有移动、合并或删除模块；新增 `interruption.rs` 集中处理恢复提交。没有修改数据库 schema 或正式数据。

取消时检查点发布不能被已经取消的 run token 立即跳过，但接收方关闭仍会结束等待。新请求替换旧请求并关闭旧接收方时，将取消过程中发生的客户端关闭保留为 cancelled，避免误记 failed；数据库等其他错误不会被掩盖。

## 验证

四项定向测试通过：

| 场景 | 恢复后的当前文字 | 更早已完成内容 | 工具行为 |
| --- | --- | --- | --- |
| TextDelta 后手动取消，再发消息 | 保留一次 | 保留 | 无自动重放 |
| 等待工具结果时取消，再 Resume | 保留一次 | 保留 | 未完成工具记为取消 |
| 同一批工具部分成功后取消 | 保留一次 | 保留且成功状态不变 | 仅取消其余调用 |
| 连续两次带部分文字的断流，耗尽重试后 Resume | 两段各保留一次 | 保留，重试历史前缀稳定 | 无自动重放 |

最终服务端全量 **348 项通过、0 失败**；Clippy all-targets（`-D warnings`）、fmt 和 diff 检查通过。完整验证结果记录在 [修复证据](2026-10-08-issue172-fix-evidence.json)。现有错误生命周期 7 项已通过，包含新请求替换旧请求的状态检查。原测试要求重试丢弃部分文字，现改为验证旧历史完整保留、部分文字加入历史、未完成工具参数不重放。

取消工具的既有测试原本在取消后不再确认 KV 消息，新行为需要发布恢复数据，因此测试补齐确认，并断言工具终止、已结算检查点、取消 EndStream 的顺序。客户端停止后仍能完成这段协议交互，须在真实 Cursor 复测中确认；客户端断开连接由已有 disconnect token 结束 blob 等待。

中断文字提交前先结束流式工具卡片，再释放排队的正文与 thinking 展示，防止 Cursor 将未结束的卡片误判。错误卡片复用现有 `compat::failure_with_message`（MCP 错误表示），不伪造 Shell 成功结果。取消后已生成但因工具尚未结束而排队的文字会保留并展示；修改原“取消即丢弃排队文字”的断言，同时检查实时与 checkpoint 重放顺序一致。
