# Issue #297：长对话中的工具性能下降

## 当前结论

2026-10-14 队列更新：用户选择以后日常使用时再观察本项，暂后置。未复现长对话性能问题、未修改生产代码，不标记已解决；下述分段调查方案留待再次出现症状时使用。

截至 2026-10-12，#297 仍为上游 OPEN。当前版本还没有足够证据把“Agent Window 变慢/占用内存升高”归因到 BYOK 服务端；先记录为 **待分段复现**，没有修改生产代码，也没有把客户端卡顿误记成服务端修复。

上游描述是约 19–20 轮对话、上下文约 250K、自动压缩约 12 次后明显卡顿，调用工具或命令可能长时间等待直到超时；另一条评论称 Agent Window 可能占用约 2 GB，而 IDE 右侧标签页感觉正常。评论没有提供请求日志、版本、模型、工具类型或客户端内存快照。

## 现版代码路径

```text
server/src/run/engine.rs
├── 发送模型请求前的上下文预检查
├── 超限时 auto_compact，并在 provider 溢出后最多再压缩重试一次
└── 压缩后重新加载检查点消息并继续执行
server/src/run/compaction.rs
└── 按用户消息边界裁剪压缩输入，保留比例化上下文余量
server/src/cursor/checkpoint/worker.rs
└── 串行处理 settled / tool-started / final / compaction 检查点任务
server/src/cursor/checkpoint/builder.rs
└── 重建 roots、turns、派生状态和 token breakdown
server/src/cursor/services/blob_sync.rs
└── 每个新 Blob 发送给 Cursor，并等待 SET ACK
```

因此需要分别记录：

1. provider `stream` 从发送到首个有效事件、完成或错误的时间；
2. `auto_compact` 的模型调用和替换检查点时间；
3. 检查点 worker 的构建/发布时间；
4. Blob SET ACK 等待时间和数量；
5. Cursor Agent Window 的渲染延迟、进程内存和工具卡片是否真正超时。

FakeProvider 或协议测试只能证明 1–4 的服务端边界，不能证明 Cursor UI 内存问题；UI 证据需要同一长对话在真实 Cursor 中采集。
