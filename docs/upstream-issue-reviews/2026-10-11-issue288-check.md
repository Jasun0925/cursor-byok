## 当前执行链路

```text
server/src/cursor/
├── services/context_sync.rs         # 缺少上下文 blob 时请求客户端补发，并缓存到 Store
├── compile/context.rs               # 读取直接/内嵌/blob MCP 定义，生成工具与 meta 路由
├── compile/run.rs                   # 每轮按当前模型和上下文组装模型请求及执行上下文
├── tools/tool_call_dispatch/exec.rs  # 将 CallMcpTool 映射为当前客户端 MCP 执行请求
├── tools/codec/                     # MCP 执行请求与返回结果编解码
└── checkpoint/                      # 保存并恢复后续回合使用的对话状态

客户端本轮模型选择 + MCP 上下文
  → 上下文加载/缓存 → 本轮工具声明和执行路由
  → 模型输出工具调用 → Cursor MCP 执行 → 工具结果进入历史
  → 发布检查点 → 下一轮换模型，重新生成工具与路由
```

MCP 声明与路由不是首次模型选择的固定缓存。仍须核对真实客户端换模型时实际传来的声明形状；服务端合成输入正常不代表客户端现场正常。

## 探针结果

| 输入路径 | A → B → A 的 MCP 执行 | 上下文重新加载次数（逐轮） | 结果 |
| --- | --- | --- | --- |
| RunRequest 直接工具列表 | 3 / 3 | 0、0、0 | 通过 |
| 内嵌 RequestContext 工具列表 | 3 / 3 | 0、0、0 | 通过 |
| MCP blob 引用的工具列表 | 3 / 3 | 1、0、0 | 通过 |
| MCP blob 中 meta 描述 + CallMcpTool | 3 / 3 | 1、0、0 | 通过 |

每组第三轮重建 TransportRegistry，沿用同一个真实 SQLite Store，并传回上一轮输出的检查点。验证模型 ID、工具声明、客户端 provider/tool/server 路由、参数和成功返回值；历史角色、内容、调用 ID 与参数均保持结构前缀。该重建不是实际进程重启。

独立发现：最初严格比较整个 ProjectedMessage 时，四组都在检查点恢复后的内部消息 ID 断言失败。对照组保持同一模型仍出现两处 ID 变化：assistant/tool-result 变为 `cursor-root:*`；内容、工具调用 ID、request-context 和 runtime ID 保留。因此将其独立记录，不把切模型 MCP 问题判为已复现，也不声称完整内部消息身份不变。供应商线上序列化和实际影响尚未验证。
