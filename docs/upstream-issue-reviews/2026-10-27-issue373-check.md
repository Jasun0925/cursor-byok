## 实际检查的路径

```text
Cursor RunRequest（合成协议请求）
  → TransportRegistry / compile/run.rs：编译动作并导入 Cursor checkpoint
  → run/engine.rs：执行手动压缩，或在普通运行前自动压缩
  → Store：保留原 checkpoint；成功压缩才替换活动历史
  → checkpoint worker：发布 KV blob 与 ConversationCheckpointUpdate
  → 模型错误结束当前 Run
  → 新运行层实例 + 已保存 SQLite / Cursor checkpoint
  → ResumeAction：读取已提交摘要和中断文字，再调用模型
```

实际经过协议解码、编译、运行循环、SQLite 和 checkpoint 发布；模型事件由 FakeProvider 提供。没有请求正式供应商，没有点击真实 Cursor UI，也没有修改正式代理或数据库。

## 场景与结果

| 场景 | 观察结果 |
| --- | --- |
| 手动压缩输出部分摘要后返回 401，再次压缩并发新消息 | 明确返回错误，不发布完成摘要；普通历史内容和顺序保持，部分摘要没有入库。重试的完整 `ModelRequest` 与失败请求相等；随后成功压缩一次，新消息正常完成 |
| 自动压缩成功，随后模型输出部分进度并返回 401，再创建运行层实例继续 | 只有一次压缩；已提交摘要和中断文字保留，恢复请求历史以失败请求为精确前缀，系统指令及工具定义不变；正常结束，没有再次压缩 |
| 自动压缩模型返回部分摘要后 401，后续模型也失败，再继续 | 现有自动压缩路径使用摘录摘要完成 checkpoint 提交，失败的部分摘要未入库；恢复保留后续文字，只有一个请求上下文，正常继续 |

每个场景恰好四次模型请求，无隐藏重跑。第三项验证恢复结构和生命周期，不证明摘录摘要的语义质量，也不能替代原服务商的压缩行为。

最初夹具遗漏 `ModelEvent::Start`，导致协议错误重试并触发测试超时；修正后另一个断言发现 Cursor checkpoint 导入会将普通 assistant 消息转换为根消息 ID。最终既检查原始内容/顺序保留，又将失败前后投影的完整身份与实际模型请求比较，并严格检查两次压缩请求完全相等。这两次夹具修正不是产品故障或生产修复。

### 审查补充：结束帧必须明确成功

[PR #5](https://github.com/haohaomin/cursor-byok/pull/5) 首次提交 `f02066107602b664b9f97a737c651b4966ab9606` 的 [CI](https://github.com/haohaomin/cursor-byok/actions/runs/40467363189) 四项检查全部通过。Sourcery 审查随后指出测试夹具只读取 `error.message`：合法错误帧可以省略该字段，会被错误视为成功。

夹具已改为明确的成功、失败和未结束状态。只有成功形状 `{}` 才通过恢复成功断言；错误必须包含 `error.code`，是否有文字不影响失败判定，无效载荷直接拒绝。新增检查使用服务端正式编码器生成无错误文字的失败帧，同时验证成功帧及八种无效载荷。补充后整个 compaction 套件 **9 项通过、0 项失败、0 项忽略**。
