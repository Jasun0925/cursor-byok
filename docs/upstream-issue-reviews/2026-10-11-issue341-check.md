# Issue #341：新版 Cursor 与检查点补充验证

## 结论

最新实机结果：用户手动确认文件区 **Undo** 和 **Restore Checkpoint** 均正常。收到第二项确认后的首次只读磁盘核对，两个测试文件都为 `value=1`。当前简单场景未复现；本轮没有生产代码修复，不将上游 Issue 标记为修复完成。下文隔离探针结论与此前 UI 限制按调查时间保留，最新现场边界见文末。

本机 Cursor 已从上次调查的 3.24.9 更新到 **3.24.12**，commit `37b865941ccb31e2fc90c685157534efca87f960`。BYOK 基线仍为 `2e2193a`。本次仅调查和探针验证，未修改生产代码、未合并或发布。

新增确认：**即使提供完整编辑快照，当前 CheckpointBuilder 也只保存编辑步骤，不派生 file_states_v2。** 将同一编辑分别交给新版客户端的 All Agent Changes 原始方法：文件状态为空时返回 0 个文件；提供相应状态和内容 blob 后返回 1 个文件。这与回调是否成功是两项独立问题。

用户现场两个回滚入口失效的具体触发条件仍未确认，不能将改动列表为空等同于 Undo/Reject 按钮实际执行失败。

- 新增：登记正常，向原生恢复方法提供合成 V0 目标检查点，内存文件从 `new` 恢复为 `old`，保存 1 次。
- 新增：回调超时丢失，再调用原生恢复方法，内存文件保留 `new`，保存 0 次，无抛错。
- 新增：originalFileStates 和 inline diff 都已登记，但 fileStatesV2 为空，All Agent Changes 返回 0 个文件。

边界：使用内存文件系统、替代服务、手动触发的 5000ms 定时器；恢复目标为合成的初始检查点，使用正确的空差异。不覆盖真实 UI、实际 RPC、真实 checkpoint 磁盘持久化或复杂 diff 算法；未自动操作 Undo/Reject 按钮。
