# Issue #300：后台 Shell 等待复核

## 结论

2026-10-09，在 v1.0.13 提交 `2e2193ad0820238b8939c2637d89c3ff7598f9f8` 上未复现服务端等待 15 秒的问题。原报告使用的 `AwaitShell` 已从当前工具集合移除，当前流程是 Shell 转后台后由 Cursor 发送完成通知。

上游 [#300](https://github.com/leookun/cursor-byok/issues/300) 查询时仍 OPEN。不能据此认定原作者问题已经解决；真实 Cursor 的进程结束到通知发出的时间尚未测量，清单保持未勾选。

## 执行边界

```text
Cursor 客户端                 执行命令、管理后台进程、发出完成通知（本次未实测）
  → BackgroundTaskCompletionAction
BYOK TransportRegistry       接收通知、恢复会话（本次协议测试）
  → FakeProvider             记录模型调用并立即返回固定结果
  → SQLite + checkpoint      保存结果；测试驱动确认 KV 写入
  → 继续操作等待窗口          模型回复后约 2 秒，随后结束连接
```

使用临时 SQLite、真实服务端 TransportRegistry、合成的客户端通知以及 FakeProvider。没有实际执行报告中的 10 秒 Shell 命令，没有调用真实供应商，不将测得延迟当成完整 UI 延迟。

## 结果

| 场景 | 观测结果 |
| --- | --- |
| AwaitShell，数字 shell_id，block_until_ms=15000 | 1.804 ms 返回工具已移除；没有派发客户端 Exec |
| AwaitShell，字符串 shell_id，block_until_ms=15000 | 0.034 ms 返回工具已移除；没有派发客户端 Exec |
| Shell 成功通知，含 tool_call_id | 9 ms 调用模型；2016 ms 结束连接 |
| Shell 成功通知，不含 tool_call_id | 5 ms 调用模型；2011 ms 结束连接 |

以上为首轮成功运行观测值，不是性能保证。回归分别限制旧工具调用在 1 秒内完成、通知后在 1 秒内调用模型，并单独等待连接收尾。初次测试把连接结束限制为 2 秒而超时；检查 `conversation/runtime.rs` 后确认这是既有的 2 秒 continuation idle window，随后将“模型开始调用”和“连接结束”分别计时，生产代码未修改。

新增回归位于 `server/tests/tool_round.rs` 和 `server/tests/conversation_delivery.rs`。当前工具声明 `server/prompt/cursor/tools.json` 没有 AwaitShell；`block_until_ms` 是 Shell 转入后台前的等待上限。

随后运行这两个测试目标中的 `shell_` 定向回归，共 5 项通过、0 失败，包含已有后台转移、终止通知及并发完成通知去重用例。该轮成功通知到模型调用分别为 35 ms、7 ms，连接结束分别为 2044 ms、2014 ms；旧 AwaitShell 分别为 2.032 ms、0.024 ms。`rustfmt --check`（两个测试文件）及 `git diff --check` 通过。两轮成功通知的模型调用延迟范围为 5–35 ms。
