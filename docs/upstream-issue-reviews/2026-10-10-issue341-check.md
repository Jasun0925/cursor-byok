# Issue #341：回滚无效调查

> 本文保留 2026-10-10 的调查时点。后续用户手动验证两个回滚入口通过，见 [2026-10-11 实测更新](2026-10-11-issue341-check.md)。

## 当前结论

用户确认当前 Cursor 的两个入口均有问题：对话 Restore Checkpoint，以及文件改动面板 Undo/Reject。本次仅调查，未修改生产代码、未触碰用户项目文件、未提交或发布。基线 `2e2193a`（v1.0.13），只读分析本机 Cursor 3.24.9 客户端。

确认两项代码事实：

1. Write/StrReplace 编辑完成后，BYOK 将编辑结果中的完整旧内容和新内容清空，只留下可能被截断的 diff；协议探针已复现。
2. CheckpointBuilder 克隆输入 base 并更新会话数据，没有根据新文件编辑生成 `file_states` / `file_states_v2` 的实现。原有字段可以随 base 保留，不等于主动更新了新文件状态。

**还不能把这两项事实直接当作按钮回滚无效的唯一根因。** 本机 Cursor 原生写文件执行器有独立的文件变更回调，负责登记旧内容；它不依赖最终 EditToolCall 提供完整旧内容。因此仍须对用户实际入口抓取一次编辑→登记→回滚证据。

## 执行路径与职责

```text
server/src/cursor/
├── tools/tool_call_dispatch/edit.rs  # 编辑前隐藏读取旧文件
├── tools/edit.rs                     # 算出新内容，构造含 before/after 的编辑结果
├── tools/codec/request.rs            # 派发带 tool_call_id 的 WriteArgs
├── tools/tool_call_result/mod.rs     # 完成边界同时裁剪模型结果和 Cursor 工具对象
├── tools/tool_call_result/gate.rs    # gate_edit 清空完整 before/after，截断 diff
├── checkpoint/steps.rs              # 将已裁剪的工具对象加入回放步骤
└── checkpoint/builder.rs            # 构造会话检查点，未派生新文件状态
```

```text
BYOK 请求编辑
  → Cursor Read：返回旧内容
  → BYOK 计算 before/after
  → Cursor Write：实际写文件，并可经独立回调登记文件变更
       └→ fileChangeTracker → tool_call_id 找到对话气泡
            → originalFileStates + updateLastCheckpointWithFileIfNotTracked
  → BYOK 编辑成功结果
       └→ gate_edit 清空 before/after → 工具卡片 + 回放步骤

用户 Restore Checkpoint
  → Cursor composerCheckpointService
  → 读取已登记的原文件状态及目标检查点
  → 计算需恢复文件 → 写回文件 / 删除新建文件
```

本机客户端 `getUrisForCheckpoints` 在 isNAL 路径使用 `originalFileStates`；这是客户端本地回滚登记，不应与服务端协议中的 `file_states_v2` 混为一谈。`file_states_v2` 另被新版改动列表及其他上下文功能使用。

## 已确认的快照丢失

通过真实 ToolDispatcher 和 codec，模拟客户端读取 `const value = 1;`，再成功写入 `const value = 2;`。分别调用 Write 和 StrReplace。

- WriteArgs 的新文本正确。
- ToolCompletion 返回成功，有 diff。
- 将工具对象经过 StepBuffer 和 protobuf 回放编码/解码后，旧内容为 None，新内容长度为 0。
- 两项“保留 before/after”断言均失败，测试退出码 101。这不是生产修复后的测试结果。

位置：`tools/edit.rs` 原先构造了完整 before/after；`tool_call_result/mod.rs` 调用共享裁剪函数；`gate.rs` 的 `gate_edit` 只要存在 diff 就无条件删除旧内容并清空新内容，即使文件很小。

客户端 `editToolDiffFallback.js` 的 Xho 在这种输入下仅解析显示用 diff，不重新构造完整 before/after。因而“界面能画出 diff”不能证明“保存了可恢复的原文件”。但恢复所需数据也可能由独立变更回调取得。

探针保存为 [2026-10-10-issue341-probe.rs](2026-10-10-issue341-probe.rs)，未留在默认测试目录以免把已知失败调查项混入常规测试。运行时将其复制到 `server/tests/issue341_probe.rs`，执行 `cargo test -p cursor-server --test issue341_probe -- --nocapture`。预期当前基线两项保留快照断言失败；后续修复时应转为正式回归。摘要及客户端文件哈希见 [evidence.json](2026-10-10-issue341-evidence.json)。

## 需要区分的后续验证

- 对话旁 Restore Checkpoint：核对原生 fileChangeTracker 回调是否到达、tool_call_id 是否匹配气泡、originalFileStates 和目标 checkpoint 是否包含文件。源码显示气泡未创建时有 5 秒等待，超时可丢弃排队登记；目前没有现场证据证明触发了该分支。
- 改动面板 Undo/Reject：确认具体入口使用的恢复数据与完整内容、file_states_v2 的关系，不能用对话回滚的实现代替判断。
- 在隔离仓库验证修改已有文件、新建文件、同一文件跨两轮编辑；检查回滚目标、磁盘内容、继续对话后的状态是否一致。
- 若着手修复，模型可见文本的限长与恢复所需的原始文件快照应分开保存；仅去掉截断可能增加历史体积，也未必补齐客户端登记。需基于实际失败路径实现，不用 Git reset 或模型反向编辑冒充 Cursor 原生回滚。

当前未完成原生 UI 验证，没有声明问题已解决。

## 两个入口的共同登记路径（补充调查）

本机 Cursor 3.24.9 的 `_handleFileChangeImpl` 在收到原生执行器的文件变更回调后，先按 `metadata.toolCallId` 找到工具气泡，再执行两组登记：

```text
Cursor 原生 Write → fileChangeTracker.trackChange(path, before, after, toolCallId)
  → _handleFileChangeImpl → 按 toolCallId 找到气泡
      ├→ originalFileStates + updateLastCheckpointWithFileIfNotTracked
      │    └→ Restore Checkpoint：按目标检查点恢复文件
      └→ _handleRegularFileChange → addDecorationsOnlyDiff
           └→ 原始行 + 新内容行 + composerMetadata
                └→ diff descriptor → Undo/Reject → inlineDiffService.rejectDiff
```

普通文本的 Undo/Reject 依赖已登记的 diff handler 及 `originalTextLines`。`composer.rejectDiff` 找不到所属会话的 diff descriptor 时会记录 `[composer] no diff id for uri` 后返回；inlineDiffService 找不到 handler 时只移除 diff 记录。由此确认，两入口共享上游文件变更回调，但最终恢复数据不同，不能统称为读取 file_states_v2。

原生 Write 的回调条件也已核对：有 tracker、未传 fileBytes、不是特定 Cursor 内部目录、文件未超过原生读取大小限制。BYOK 的 edit_write_request 传 file_text、空 file_bytes 和 call.call_id，未发现普通文本写入主动禁用回调。工具开始消息和 WriteArgs 均使用 call.call_id；静态检查没有发现这两个字段直接错配，仍不能证明实际气泡创建时序正确。

若气泡查找失败，客户端会暂存回调并最多等待 5 秒；等待失败会删除暂存项。**这是可能同时影响两个入口的失败路径，尚无证据证明用户现场走到了它。**

本次搜索已有 Cursor 日志中的原始文件缺失、diff id 缺失、toolCallId 缺失和检查点相同等精确日志文本，没有命中。这不能证明登记正常，相关分支可能没有日志或日志不在当前保留范围内。

本次读取 Cursor 界面返回 macOS ScreenCaptureKit `-3811`，未执行编辑或回滚点击。现场根因仍待验证，生产代码保持未修改。

## 2026-10-10 原生回调隔离验证补充

已用本机 Cursor 包内的原始 writer、tracker、气泡查找、等待注册表、文件变更 handler 和 checkpoint 方法建立隔离探针。12 项场景符合断言：正常路径可登记；超过 5 秒以及无关联会话的同名工具 ID 条件下可丢登记。原生 Write 返回 success 而恢复登记为空的组合已在内存文件系统中复现。客户端界面与执行请求分属并发队列，服务端先发开始消息不足以保证气泡已创建。

仍未完成用户现场 UI/RPC 复现，不把这些条件直接定为用户故障根因。具体控制流、边界和可运行证据见 [登记回调专项调查](2026-10-10-issue341-callback-check.md)。
