## 当前代码路径

```text
server/src/
├── cursor/tools/codec/request.rs   # 将 Shell 参数编码成 Cursor 执行请求
├── cursor/tools/runtime.rs         # 持有尚未完成的工具调用和流式输出
├── cursor/tools/codec/response.rs  # 处理开始、输出、退出、后台化等客户端事件
├── run/tool_round.rs               # 等待工具结果或取消，提交结果到存储
└── cursor/conversation/            # 对话输入、结果交付及后台完成通知
```

```text
模型发起 Shell
  → BYOK 编码 ShellStreamArgs
  → Cursor 客户端处理批准与进程执行
  → stdout/stderr：更新输出，调用仍未结束
  → Exit：返回完成结果
     或 Backgrounded：返回后台任务信息 → 后续完成通知链路
  → BYOK 保存工具结果 → 模型继续处理
```

- `block_until_ms` 默认 30,000，编码为 `timeout`；`timeout_behavior=Background`。这不是“运行 30 秒就杀死命令”。
- 另向 Cursor 传递 `hard_timeout=86_400_000`（24 小时）；这是请求参数，不证明客户端实际计时和执行一定正确。
- `Start`、`HookContext` 事件保持 Pending；stdout/stderr 作为增量，Exit 与 Backgrounded 才在这一阶段生成工具结果。
- `run/tool_round.rs` 等待工具结果或取消的循环没有自身审批倒计时；仅此不足以排除客户端、传输和后台完成通知中的时间边界问题。
- 既有 `shell_uses_background_timeout_and_preserves_stream_identity` 测试构造 Backgrounded 事件，覆盖参数及结果映射；并非真实等待批准或运行 20 分钟的证据。本轮尚未运行该测试。

## 后续最小复测

1. 隔离环境中产生确实需要批准的安全命令，延迟批准超过其等待阈值；分别记录请求发出、批准、进程启动、退出的时刻，确认不会提前产生执行超时或重复运行。
2. 运行超过 20 分钟的低资源命令，输出明确的开始/结束标记。记录是否转入后台、进程是否正常退出、Cursor 是否发送完成通知、BYOK 是否接收、Agent 是否继续。
3. 协议探针和真实 Cursor 测试分别记录。短命令通过或人为发送后台完成事件不能替代长任务实测。

## 合成协议测试

在上述基线通过实际 TransportRegistry、run 和 checkpoint 路径，使用 FakeProvider 与合成客户端分别验证：

1. 发出 Shell 执行请求后，客户端 35 秒内不发 Start，也不返回结果。

两例均使用 `block_until_ms=3000`，验证 Background 与 24 小时硬超时参数；等待期间处理 checkpoint ACK。等待结束前没有工具提前完成、模型续轮或重复执行请求；随后注入成功 Exit，工具正常完成，模型继续并结束。

结果：**2 passed / 0 failed，37.17 秒**。探针源码见 [issue155-probe.rs](2026-10-15-issue155-probe.rs)。这里只证明服务端在所覆盖的静默客户端事件序列中没有自行制造超时；没有真实 Shell、真实审批或 20 分钟等待。

## 结论与下一步边界

不能据此称“完全正常”，也不能直接归因为原报告中的 20 分钟超时。已观察到**后台命令正常结束但没有自动续答**；尚未做短后台命令对照、显式 `notify_on_output` 对照，未确认此版 Cursor 在不登记输出通知时的默认完成通知规则。因此本轮不把它标记为已修复或已完整复现 #155。

若继续调查，应先以短命令对照区分默认完成通知与显式输出通知，再检查客户端是否登记任务、发出通知，以及通知进入 BYOK 后的处理。无需为了证明服务端接收链路而伪造客户端事件并称作实机通过。
