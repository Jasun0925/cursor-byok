## 当前路径与验证

```text
Cursor UserMessageAction → 活动父 Run
                           ├─ 保留仍在执行的 Task
                           ├─ 追加用户消息 → 模型继续
                           └─ Task 完成 → 原结果交付一次 → 模型继续

父 Task → SubagentArgs.model_id → Cursor 构造子代理请求（本轮没有实测此客户端环节）
                                  ↓
子代理 RequestedModel.parameters → compile/model.rs → ModelConfig.configure
                                  ↓
                               ProviderRouter → 实际 HTTP JSON
```

1. `server/tests/interrupt.rs` 新增两个 UserMessageAction 场景，复用已有 Task 生命周期验证：子代理未完成时，父模型已收到追加消息；子代理保留执行，父模型回复前或回复后到达的结果均只交付一次。重复终态不重复调用模型；检查历史前缀、最终 checkpoint 和原 Task 完成事件。连同既有取消、队列、注入与压缩边界，**23 项通过**。这是合成 Cursor 协议和 FakeProvider，不能代替客户端真的把排队消息发出来。
2. `server/tests/subagent_reasoning.rs` 通过真实 TransportRegistry、编译、配置及 ProviderRouter 向临时 loopback HTTP 服务发送请求。OpenAI Chat 与 Responses 各覆盖五组，共 **10 次请求、2 项测试通过**：

| 请求角色 | 请求 reasoning | 保存的 reasoning_effort | 实际 HTTP effort |
| --- | --- | --- | --- |
| 父角色对照 | max | low | max |
| 子代理 | high | low | high |
| 子代理 | max | low | max |
| 子代理 | 未给出 | medium | medium |
| 子代理 | max | none | 不传 |

每组均恰好发送一次 HTTP 请求并正常结束；故意使用不同显示标签，确认标签不会替代结构化参数。`none` 是 BYOK 已有的显式“不传入”配置。各组请求由测试构造，不是客户端从父代理自动继承后捕获的请求；未使用原中转站或真实供应商模型。

初次 HTTP 测试夹具因缺少 `tooltip_data` 未能创建模型，修正夹具后通过；这不是产品故障基线。没有为得到“修复”而修改参数优先级或猜测 Max 标签含义。

验证命令：`cargo test --package cursor-server --test interrupt`（23 项）、`cargo test --package cursor-server --test subagent_reasoning`（2 项）；两份测试的 Clippy `-D warnings`、`cargo fmt --all -- --check` 和 `git diff --check` 均通过。测试服务使用随机 loopback 端口，未使用正式凭据。

## 结论与后续

上述协议和 HTTP 路径没有复现卡住或参数被错误改写。要定位原问题，需要在 Cursor 实际场景中同时记录排队消息是否发出、父/子 Run 的请求参数、Task 的 model_id、供应商 HTTP body，以及卡片标签出现的时间。界面工具此前持续返回 macOS `-3812`，本轮没有进行实际 Cursor 点击测试。

本轮只使用临时测试数据库和 loopback 端口；未修改正式代理、正式数据库或 Cursor 审批设置。上游归档只读，没有发送评论，也未关闭原 Issue。
